## O que muda em relação ao `users-api`

### 1. Nome do serviço e caminho dos arquivos

- Fallback do `OTEL_SERVICE_NAME`: **`"catalog-api"`**.
- Arquivo: `src/Fcg.Catalog.Api/Extensions/ObservabilityExtensions.cs`, namespace
  `Fcg.Catalog.Api.Extensions`.
- Pacotes no `src/Fcg.Catalog.Api/Fcg.Catalog.Api.csproj`.

### 2. ⚠️ Conflito de versão de pacote — leia antes de rodar `dotnet add`

O `Fcg.Catalog.Api.csproj` **já tem pins manuais** por causa de vulnerabilidade transitiva:

```xml
<PackageReference Include="Microsoft.OpenApi" Version="2.7.5" />
<PackageReference Include="SharpCompress" Version="0.49.1" />
<PackageReference Include="Snappier" Version="1.3.1" />
```

Depois de adicionar os pacotes de OpenTelemetry, rode `dotnet list package --vulnerable
--include-transitive` e `dotnet build -warnaserror:NU1903` para confirmar que **nenhuma
vulnerabilidade nova entrou** e que os pins continuam válidos. Se um pin passar a ser
*downgrade* (o OTel exigir versão maior), **atualize o pin** — nunca remova.

### 3. Instrumentação do MongoDB — aqui vale mais a pena

O `catalog-api` é o serviço com mais I/O de banco da plataforma (catálogo, biblioteca, pedidos,
avaliações). Vale instrumentar o driver do Mongo para o trace mostrar **quanto tempo é banco**:

O driver 3.x do Mongo expõe uma `ActivitySource`. Ative-a no `WithTracing`:

```csharp
                // Spans das operações do MongoDB: é o que responde "a lentidão é o app ou o banco?"
                // sem chutar. O nome do source vem do driver — CONFIRME com:
                //   dotnet run e então `curl /metrics`, ou inspecionando
                //   MongoDB.Driver.Core.Extensions.DiagnosticSources / a doc da sua versão.
                // Se o source não existir na versão instalada, remova esta linha: um AddSource com
                // nome inexistente é silenciosamente ignorado, o que ESCONDE o problema.
                .AddSource("MongoDB.Driver.Core.Extensions.DiagnosticSources")
```

> Se não conseguir spans do Mongo em 15 minutos, **desista disso e siga** — não é requisito.
> Registre como melhoria futura. O que é requisito são as métricas HTTP.

### 4. `MapPrometheusScrapingEndpoint` e a ordem do pipeline

O `catalog-api` **não tem** `UseRateLimiter`, então a preocupação com 429 no `/metrics` não se
aplica. Mas ele tem `[Authorize]` no nível de classe em vários controllers — confirme que o
`/metrics` (que é *endpoint*, não controller) fica **fora** da autenticação:

```bash
curl -i http://localhost:8082/metrics    # DEVE ser 200 sem Authorization
```

### 5. O trace distribuído da compra — este serviço é o protagonista

O fluxo "Compra de Jogo" do desafio **começa** aqui: `POST /api/v1/biblioteca` → `OrderPlacedEvent` →
`payments-api` → `PaymentProcessedEvent` → volta para o `PaymentProcessedConsumer` **deste** serviço.
Para o trace atravessar tudo, dois pontos:

1. `.AddSource("MassTransit")` no `WithTracing` (já está na receita do `users-api`).
2. **O outbox transacional pode romper a correlação.** O `catalog-api` usa `AddMongoDbOutbox` com
   `UseBusOutbox()`: a mensagem é gravada no Mongo dentro da transação e entregue ao broker depois,
   por um *delivery service* — em **outro** contexto de execução, possivelmente segundos depois. Se o
   contexto de trace não for persistido junto da mensagem, o span do consumer nasce como **trace
   novo**, e o Jaeger mostra dois traces separados em vez de um.

   **O que fazer:** valide isso empiricamente (passo "Como validar" abaixo). O MassTransit 8 persiste
   os headers de trace no outbox, então **deve** funcionar. Se não funcionar:
   - **não invente workaround** — a correlação `catalog → payments` pelo `ConversationId` do
     MassTransit já é suficiente para o vídeo;
   - registre o achado num comentário desta issue e crie uma issue de follow-up;
   - mencione a limitação no README (isso conta como maturidade técnica, não como falha).

## Como validar

Rode tudo o que está em `users-api#19`, trocando a porta para `8082`, e **mais** estes:

```bash
# 1) Métricas HTTP presentes
curl -s http://localhost:8082/metrics | grep http_server_request_duration_seconds_count

# 2) O TRACE DISTRIBUÍDO DA COMPRA — o entregável extra da fase
TOKEN=$(curl -s -X POST http://localhost:8081/api/v1/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"admin@fcg.com","senha":"Admin@123456"}' | jq -r .accessToken)
JOGO=$(curl -s http://localhost:8082/api/v1/jogos | jq -r '.itens[0].id')
curl -s -X POST http://localhost:8082/api/v1/biblioteca -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d "{\"jogoId\":\"$JOGO\"}" | jq

sleep 10
open http://localhost:16686
# Service: catalog-api -> Operation: POST /api/v1/biblioteca -> Find Traces
# O QUE PROCURAR no trace: spans de catalog-api (HTTP + publish), payments-api (consume + publish)
# e catalog-api de novo (consume). Se aparecerem como traces SEPARADOS, veja o item 5 acima.
```
